Modular Monolith Cheat Sheet

Kotlin + Spring Boot 4 · Spring Modulith 2 · kotlin-result

Module Structure

products/
├── products-api/    # public contract
└── products-impl/   # everything else, internal

Dependency rules

FromMay depend on
x-implown -api, other -apis, common
x-apilower-level -apis, common
testFixturessame rules as main code
applicationall -impl modules
Never: -impl → other -impl, -api → -impl, cycles.
Arrows point down. Foundations (Products, Users) know nothing above them. Need to go up? Event or SPI.

What Lives Where

-api (public)

  • Service interfaces: ProductServiceApi
  • DTOs and value types: ProductDto, ProductId
  • Events: ProductRenamedEvent
  • Sealed errors: ProductError
  • SPIs: ProductDeletionBlocker
  • testFixtures: builders, FakeProductService, contract tests

-impl (internal)

  • Domain model with behavior: Product, Money
  • Service implementations, handlers
  • Persistence, migrations, controllers, listeners

common (shared kernel)

  • A few stable types: Money, Email, the Result setup
  • No business logic, no types owned by one module

Data Isolation

CREATE SCHEMA shipping;
CREATE ROLE shipping_module LOGIN;
GRANT USAGE ON SCHEMA shipping TO shipping_module;
GRANT SELECT, INSERT, UPDATE, DELETE
  ON ALL TABLES IN SCHEMA shipping TO shipping_module;

CREATE TABLE shipping.shipment (
  id           VARCHAR(255) PRIMARY KEY,
  product_id   VARCHAR(255) NOT NULL, -- no FK
  weight_grams INT NOT NULL           -- copied
);
Never: cross-schema joins, writes or foreign keys.
Run module tests as the module's role: a stray join fails in CI.

Synchronous Calls

val product = productService.getProduct(id)
    .getOrElse { return Err(ShipmentError.ProductNotFound(id)) }

Translate at the boundary

internal class ProductAdapter(
    private val productService: ProductServiceApi,
) {
    fun getShippableItem(id: ProductId): ShippableItem? {
        val dto = productService.getProduct(id).get() ?: return null
        return ShippableItem(id, dto.weightGrams, ...)
    }
}
Keep chains short (one or two hops) and keep one module per transaction.

orders.map { OrderSummary(it, products[it.productId]) }

Events

Persist them: the registry is your outbox

implementation(
    "org.springframework.modulith:spring-modulith-starter-jdbc"
)
spring.modulith.events.republish-outstanding-events-on-restart=true
  • At-least-once delivery: make listeners idempotent
  • Events are stored contracts: add fields with defaults, never rename
Never: a bare @TransactionalEventListener that writes. It runs on the caller's thread and its writes are lost.

Errors as Values

// products-api
sealed interface ProductError {
    data class NotFound(val id: ProductId) : ProductError
    data class InvalidData(val reason: String) : ProductError
    data object DuplicateName : ProductError
    data object DeletionBlocked : ProductError
}

interface ProductServiceApi {
    fun getProduct(id: ProductId): Result<ProductDto, ProductError>
}

To HTTP, at the controller

@GetMapping("/products/{id}")
fun getProduct(@PathVariable id: ProductId): ProductDto =
    productService.getProduct(id)
        .getOrElse { throw it.toResponseStatusException() }

private fun ProductError.toResponseStatusException() = when (this) {
    is NotFound    -> ResponseStatusException(NOT_FOUND)
    is InvalidData -> ResponseStatusException(BAD_REQUEST, reason)
    DuplicateName   -> ResponseStatusException(CONFLICT)
    DeletionBlocked -> ResponseStatusException(CONFLICT)
}  // no else: a new error won't compile until it's mapped
Result if the caller can act on it. Throw if the operation should abort.

SPI: Ask Without Knowing

// products-api/spi
interface ProductDeletionBlocker {
    fun canDelete(productId: ProductId): Boolean
}

// orders-impl implements it; products-impl collects them all
private val deletionBlockers: List<ProductDeletionBlocker>

if (deletionBlockers.any { !it.canDelete(id) }) {
    return Err(ProductError.DeletionBlocked)
}

Fake + contract, shipped in -api testFixtures

abstract class ProductServiceContract {
    abstract val service: ProductServiceApi
    abstract fun givenProduct(product: ProductDto)

    @Test
    fun `returns NotFound for an unknown id`() {
        val id = ProductId("unknown")
        assertThat(service.getProduct(id).getError())
            .isEqualTo(ProductError.NotFound(id))
    }
}
// runs against FakeProductService and ProductServiceImpl
Test behavior, not calls. Builders with defaults:
buildProductDto(weightGrams = 500)

Putting It Together

project-root/
├── build-logic/      # conventions, module validation
├── common/           # shared kernel
├── products/
│   ├── products-api/
│   └── products-impl/
├── orders/, shipping/, ...  # same shape
└── application/      # composition root, all -impl
// application/build.gradle.kts
implementation(project(":products:products-impl"))
implementation(project(":orders:orders-impl"))
// ./gradlew :application:bootJar → one JAR
  • Module name in logs and metrics
  • Separate executors for heavy listeners
  • Timeouts on everything shared

With Coding Agents

  • One module + the -apis it uses fits in a context window
  • Every rule the build checks is feedback the agent fixes itself
  • Fast per-module checks: ./gradlew :orders:orders-impl:check
  • An AGENTS.md per module: what it owns, publishes, listens to, its invariants
  • Build files and validation rules under CODEOWNERS
  • Humans review the seams: -api, events, migrations, new dependencies
Never let an agent "fix" a boundary violation by adding a dependency.
